# RDS MySQL 8.0.45 Online Modify XMind 场景化 Markdown 设计

## 背景

源文件为：

`outputs/online_modify_xmind_20260910_v3/RDS_MySQL_8.0.45_测试计划反串讲_V3_逐项通俗说明版.xmind`

源 XMind 使用新版 `content.json` 格式，包含 3 个工作表、7,317 个主题节点：

- 96 个测试维度及 497 个直接因子取值；
- 48 个综合场景；
- 302 个原编号检查点、1,602 条原始用例、155 条语法索引、35 个公共因子和 16 个契约待决项。

V3 已完整包含 V1、V2 的测试语义。需要解决的问题不是旧内容缺失，而是现有综合场景只列出了关联维度名称，没有逐场景明确前置条件、因子覆盖口径和观测点。

## 目标

在不修改源 XMind 的前提下，在同一输出目录新增一份场景优先的完整 Markdown。Markdown 必须：

1. 以 SC01～SC48 为主体，便于评审和执行；
2. 为每个场景补齐前置条件、覆盖因子和观测点；
3. 使用“全部覆盖”等范围声明表达覆盖责任，不展开无意义的全量笛卡尔积；
4. 保留原始测试点、公共因子、用例和契约的追溯关系；
5. 保留源 XMind 中的测试点目录和追溯附录，不把内容简化为只有 48 个场景的摘要。

## 非目标

- 不修改或覆盖原 XMind；
- 不声称任何尚未执行的用例已经通过；
- 不编造产品参数、内部同步点、故障注入 API 或未冻结的产品契约；
- 不把“全部覆盖”解释为所有因子的全笛卡尔积；
- 不将不兼容的表结构或索引类型强行放入同一张物理表。

## 输出文件

输出文件位于源 XMind 同目录，建议命名为：

`RDS_MySQL_8.0.45_测试计划_V4_场景化完整覆盖版.md`

文档采用 UTF-8，使用稳定的场景编号、测试点编号和锚点，便于全文搜索和后续生成执行清单。

## 文档结构

1. 文档说明与覆盖口径；
2. 全局环境和公共前置条件；
3. 全局因子目录：96 个维度及其取值、说明、构造方法和检查重点；
4. SC01～SC48 场景化测试设计；
5. 原始用例、语法、公共因子、契约待决项和原编号检查点附录；
6. 完整性统计与追溯校验结果。

场景章节按原来的 8 个场景族分组，场景顺序及 P0/P1/P2 优先级保持不变。

## 单场景统一结构

每个场景固定包含以下部分：

### 1. 场景目标

- 说明业务目标、主要风险、目标修改和预期资格；
- 明确场景是一组有编号的子运行，不是一条 SQL 或一次执行。

### 2. 前置条件

按场景实际需要填写：

- 平台、完整版本和内核构建；
- 固定功能开关及范围外开关；
- 单机或主备拓扑、复制健康状态；
- 权限、SQL mode、页大小、行格式、表空间等环境条件；
- 表结构和初始数据夹具；
- 并发会话、事务、负载、故障或恢复入口；
- 超时、停止、恢复和清理条件。

不存在正式入口或契约未冻结时明确标记 `BLOCKED` 或“契约待决”，不得用假设补齐。

### 3. 覆盖因子

按以下格式逐类声明场景覆盖责任：

| 因子类别 | 覆盖要求 | 具体范围或例外 | 执行策略 |
|---|---|---|---|
| 表结构 | 全部覆盖 / 指定覆盖 / 不适用 | 所有表型，或列出场景限制 | ALL / 边界 / 两两 / 风险组合 / 专属子运行 |
| 索引类型 | 全部覆盖 / 指定覆盖 / 不适用 | 所有兼容索引，特殊索引独立子运行 | 同上 |
| 数据和值 | 全部覆盖 / 指定覆盖 / 不适用 | 典型值、边界值、NULL、空值、非法值等 | 同上 |

“全部覆盖”的语义是：覆盖全局因子目录中与本场景兼容且适用的全部取值。存在产品限制、语法不兼容或专属场景时，必须在“具体范围或例外”中说明，并指向相应专属场景。

每个场景至少检查以下因子类别并给出覆盖声明或不适用原因：

- 环境与功能范围；
- 表类型、存储和物理状态；
- 目标列类型、属性及非目标列；
- 索引、主键、外键、生成列和分区依赖；
- 数据值、规模和分布；
- ALTER 语法、算法、锁和同句动作；
- 并发、事务、DDL 阶段和 row log；
- 主备、故障、恢复及客户端；
- 结构、数据、索引、约束、性能和交付判定。

### 4. 子运行组合

仅在需要落地关键交互时列出子运行表。普通因子使用等价类、边界值或两两组合；以下高风险交互保留强制组合：

- 类型 × 行格式 × 存储位置 × 索引长度；
- 目标列 × PK/UK/FK/生成列/分区角色；
- 算法 × 锁 × DDL 阶段 × 并发 DML；
- 唯一冲突序列 × 扫描阶段 × 事务提交顺序；
- 故障类型 × 注入阶段 × DDL 持久提交状态；
- binlog 配置 × DDL/DML 终态 × 主备恢复。

### 5. 执行步骤

保留原场景执行顺序并补齐可执行时间线：状态核验、准备夹具、启动负载、执行 DDL、命中目标阶段、执行并发或故障动作、确认终态、等待复制追平、完成核验和清理。

### 6. 观测点

“观测点”是场景执行期间需要采集和判断的现象，不是故障注入点。每个场景按适用性覆盖：

- DDL 请求、排队、MDL、扫描、增量回放、最终切换、持久提交和响应返回阶段；
- 实际算法、锁级别、持续写提交能力和错误阶段；
- 并发事务的提交、回滚、等待、超时、死锁或取消状态；
- 表结构、列属性、数据、索引访问路径、约束和后续读写；
- 主备位点、复制追平、切换和恢复状态；
- 数据库错误日志、临时对象、文件、锁和资源清理；
- 性能场景中的吞吐、延迟、CPU、IO、日志量、空间峰值和复制延迟。

每个观测点写明观察对象、证据和通过/失败判定，避免只有“检查正常”的空泛描述。

### 7. 预期结果与验收

保留原预期，并按适用性补齐：算法和锁、独立数据 Oracle、结构、数据、索引、约束、在线能力、主备、失败原子性、恢复、性能及证据要求。

### 8. 来源与追溯

保留并展开：

- 关联的新测试维度及具体取值；
- 原编号测试点；
- 公共因子 ID；
- 原始用例 ID；
- 契约待决 ID；
- 相关专属场景或范围外场景。

## 因子填写规则

1. 原场景明确列出的取值优先，不能被泛化标签覆盖；
2. 用户要求的“所有表”“所有索引”“所有值”等直接写为“全部覆盖”，同时引用全局因子目录；
3. 仅对与场景机制兼容的取值负责；不兼容项写例外或转交专属场景；
4. MVI、FULLTEXT、SPATIAL、函数/生成列、外键和分区等特殊载体使用独立子运行；
5. 故障和性能场景选取已通过语义验证的高风险代表表型，不与全部功能因子相乘；
6. 全部 96 个维度都必须至少在一个场景中被明确挂接；原先未挂接的存储引擎、列数量、表历史、数据页状态、索引数量和索引覆盖关系必须补齐；
7. 不适用、范围外、契约待决和环境阻塞分别标记，不能计为 PASS。

## 转换和内容生成策略

1. 从 XMind `content.json` 读取 3 张工作表，保留原始标题、层级、备注、链接和 ID 文本；
2. 从现有场景定义和 96 维度反向构造每个场景的覆盖声明；
3. 根据场景族、原关联维度、原测试点和用例来源定制前置条件与观测点；
4. 对“全部覆盖”补充兼容性例外，避免错误承诺；
5. 把完整原始内容作为附录保留，使 Markdown 成为可独立使用的完整版本；
6. 生成后执行结构、编号、数量和追溯校验。

## 验证与验收标准

生成结果至少满足：

- SC01～SC48 各出现一次，顺序、名称和优先级正确；
- 每个场景均包含 8 个统一部分；
- 每个场景均有前置条件、覆盖因子、执行步骤、观测点、验收和追溯；
- 每个场景的覆盖因子至少涉及表结构、索引类型、数据和值，或明确写出不适用原因；
- 96 个维度全部至少被一个场景覆盖；
- 302 个原编号检查点、1,602 条原始用例、155 条语法索引、35 个公共因子和 16 个契约待决项均保留；
- 文档中不出现未解释的待填写标记或占位内容；
- 源 XMind 的哈希在生成前后保持不变；
- Markdown 标题层级、表格和内部锚点通过静态检查。

## 风险控制

- 将“全部覆盖”限定为“全部适用取值”，并明确例外，防止把非法组合当成执行要求；
- 对内部观测能力缺失的场景保留阻塞状态，不用固定等待伪造阶段命中；
- 对故障、性能和大表场景保留并发、持续时间、空间、超时和清理边界；
- 只新增 Markdown 和生成/验证所需文件，不触碰工作区已有无关改动。
